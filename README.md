# ⚡ ST-Cache-Optimizer · 酒馆缓存优化

让 SillyTavern 发出去的提示词**两轮之间开头尽量一字不差**，从而命中 Gemini / Vertex AI 的隐式缓存（以及其他按前缀计费的缓存）。缓存命中的输入 token 通常只按原价的一小部分计费（Vertex Gemini 为 1/20）。

**不改任何文件**：世界书、预设、角色卡都原样不动。扩展只在每次生成时现场调整本次请求，关掉开关立即恢复原样。

## 为什么命中率会是 0

Vertex / Gemini 的缓存有两条规则（实测）：

1. **开头的系统提示**（第一条对话消息之前的所有 system 消息）必须**整段一字不差**，差一个字整段都不命中。
2. 系统提示之后的内容按**前缀**命中，遇到第一个不同的字就停。

常见的角色卡和预设恰好违反了第 1 条：

| 每轮都会变的东西 | 常见位置 |
|---|---|
| 关键词触发的世界书条目（提到什么就插入什么） | 角色定义前 / 后 → 系统提示 |
| MVU 等变量块（`<status_current_variables>`）、随机宏、时间宏 | 世界书常驻条目 |
| 记忆扩展的摘要（如柏宝书的「记忆系统私密简报」） | 聊天记录最前面 → 系统提示 |
| 按深度插在聊天记录中间的条目 | 每多一轮位置就后移，改写上一轮的前缀 |

## 它做了什么

1. **世界书现场调整**（`WORLDINFO_ENTRIES_LOADED`，只改本次扫描的临时副本）
   - 角色定义前/后的**关键词条目**、**会变的常驻条目**（MVU 变量、随机/时间宏、概率触发、粘性/冷却/延迟）→ 聊天中深度 0，并用 `<当前剧情相关设定>` 包住。
   - 按深度插入的**关键词 / 会变条目** → 深度 0（深度设得比聊天记录还大时，它们会落进系统提示）。
   - 按深度 / 作者注释插入、**内容固定的常驻规则** → 聊天记录之前：预设的「角色定义前」排在聊天记录前面时放进去，否则插在聊天记录最顶端并用 `<固定设定>` 包住。
   - 输出格式、破限等必须留在末尾的条目保持原位（可在设置里用正则调整）。
   - （可选，默认关）**关键词设定放到聊天记录前并保持几条消息**：关键词条目插在聊天记录最顶端、用 `<近期剧情设定>` 包住，并临时设为粘性 N 条消息（默认 6）。场景稳定时这块几轮不变，它和后面的整段聊天记录都能命中缓存；换场景、设定变化的那一轮，连聊天记录也会不命中。适合长时间待在同一场景的玩法，开几轮对比真实命中率再决定。**Gemini / Vertex 或开启提示词后处理（合并 / 半严格 / 严格）时自动不生效**：这些情况下聊天记录前的 system 块会被并成一条大消息，而 Vertex 实测只在消息边界上命中缓存，设定一变整条大消息都不命中。
2. **发送前重排**（`CHAT_COMPLETION_PROMPT_READY`）
   - 按消息角色和顺序比对聊天历史，短消息需完整匹配。无法确认连续历史，或请求包含工具调用、模型签名及多模态消息时，跳过发送前重排。
   - 将聊天记录中间可移动的 system 块和开头已识别的易变块移到历史之后，让稳定内容留在前缀中。
   - 认不出聊天记录范围时（历史被大量改写、窗口移动），不再整轮放弃：仍把**已确认的易变块**移到末尾，稳定块顺序保持不动。
3. **自动学习**：识别「同一个块」时忽略第一行里的数字、序号和引号，所以 `第 3 轮记录` 和 `第 4 轮记录` 会被当成同一块，`〔记忆系统私密简报 · 第 12 轮〕` 也能跨轮认出来。三种情况会记成易变块并从当次请求起后移：
   - 同一块**内容变过两次**；
   - 上一轮有的块**这一轮消失了**（会来回出现的世界书条目）；
   - 已经标记过的块再次出现。
   只出现一次的新块不动它，避免把稳定内容也挪到尾部、白白损失可缓存前缀。
4. **真实发送对比**：观察浏览器发往酒馆后端的请求和收到的响应，不修改请求或额外调用模型。同组请求对比消息字符前缀，**并指出断点落在哪一块、前后原文各是什么**，例如「变化所在块开头：〔记忆系统私密简报」「原文：…第 12 轮…」「现文：…第 13 轮…」。同时给出相同前缀的 token 粗估；响应提供缓存 token 和输入 token 时显示输入缓存比例；服务端报告 0 命中时，按前缀形状区分是「上游没启用缓存」还是「前缀中途断了」。诊断记录只留在当前页面内存中。
5. **免费稳定性检查**：只组装、不发送，模拟「上一轮」和「这一轮」的提示词，报告系统提示是否一致、两轮相同前缀的比例、断点所在块与前后原文、前缀 token 粗估。

## 安装

酒馆 → 扩展程序 → 安装扩展程序，填入本仓库地址；或把本目录放到
`public/scripts/extensions/third-party/ST-Cache-Optimizer/`，刷新页面。

### TauriTavern iOS 自签版

2.5.0 支持 TauriTavern 的第三方前端扩展加载方式。适配以 [上游 `85dc990`](https://github.com/Darkatse/TauriTavern/tree/85dc990) 的源码接口为基准。扩展可加载到已签名的应用里，无需改动或重新签名 IPA。

- 如果已把 2.5.0 内容发布到扩展的 Git 仓库，在 TauriTavern 里打开「扩展程序 → 安装扩展程序」，填 Git 仓库根地址。如果放在单独分支，把分支名填入安装弹窗的「分支或标签」字段。
- 如果可以访问应用的数据容器，解压后将 `st-huancun` 目录放到应用数据根目录下的 `data/default-user/extensions/`，确认 `manifest.json` 直接在扩展目录里，然后重启 App。若已安装同一扩展，请更新原有目录，避免同时加载两个副本。系统「文件」App 是否能看到该目录取决于构建方式。
- 用普通「对话补全」，在同一聊天、同一模型下连续生成两轮，查看「真实请求对比」和「输入缓存比例」。TauriTavern 的聊天记录按窗口加载，因此此环境只使用真实请求诊断。缓存比例需要响应带有对应的 token 统计。

## 使用

- **开关**：左下角魔法棒菜单里的「缓存优化：开/关」，点一下即可开启或关闭（关闭时闪电图标变暗）；扩展设置面板里也有勾选框。
- 换了新卡 / 新预设后，点「检查缓存稳定性（免费）」：
  - 先看开头系统消息是否一致，再看共同前缀长度和首处差异的位置。
  - 字符前缀用于排查提示词变化。实际输入缓存比例以服务端响应的 token 用量为准。
- 搭配记忆扩展时，让旧楼**攒批折叠**（每 N 轮折叠一次）而不是逐楼滑动，聊天记录开头才能保持不变。

## 2.6.0 改了什么

针对一张带工具调用的长卡（gemini-4-argon）命中率只有 2.6% 的实测反馈，定位到两个确凿缺陷并修复：

- **工具调用不再让整个前缀优化瘫痪**：原来只要请求里有工具调用、模型签名或多模态数组，发送前重排就整体放弃（`移动 0 个块`），所有易变块都留在前缀里。现在改成「分段保护」——工具调用链、签名、多模态只保护自己所在的局部区间，区间之外的可移动 system 块照常挪到历史之后。
- **学习范围扩大到聊天记录中间**：原来只观察聊天记录最前面（第一条非 system 消息之前）的 system 块，插在历史中间、每轮变化的记忆块/世界书条目根本学不到。现在把聊天记录中间的 system 块也纳入观察，识别出易变后立即移出前缀。

诊断里「第 11 条 (system)，序列化位置 47」这类提示，指的是第 11 条 system 消息的第 47 个字符开始变化——通常就是某个每轮被改写、但既没被标记也没被移动的块。2.6.0 会把这类块认出来并移走。

## 2.5.0 改了什么

2.4.5 的自动学习用「块的第一行」当身份。可是世界书合并后的块、按轮改写的状态块，第一行本身就在变，所以永远学不到，实际只有默认那几个易变块会被后移——这就是看完面板仍然「没有提升」的主要原因。

- 身份改为忽略数字、序号、引号的结构化标识，跨轮能认出同一块，学习才真正生效。
- 新增「块消失」这一信号：时有时无的世界书条目会在第一次消失时就被认出来，之后固定放在尾部，不再每轮截断前缀。
- 只出现一次的新块不移动，避免把稳定内容挪走反而损失可缓存前缀。
- 历史识别失败时，仍会移动已确认的易变块，不再整轮放弃。
- 断点报告从「第几条、第几个字符」升级为「哪一块、前后原文」，并给出前缀 token 粗估；0 命中时直接判断是上游没开缓存还是前缀断了。

## 注意

- Vertex 隐式缓存实测：间隔 1～12 分钟都能命中，20 分钟已过期。

- 只支持对话补全（Chat Completion）接口。
- 改设置 / 切换预设 / 开关条目后的第一轮一定不命中；两轮间隔太久缓存会过期。
- 关键词条目默认移到了聊天记录之后（开启「保持几条消息」后改为聊天记录之前，与多数预设原本的位置一致），模型参考它们的位置变了，一般影响很小；介意的话关掉「世界书现场调整」即可。
